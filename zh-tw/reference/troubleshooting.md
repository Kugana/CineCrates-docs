# 疑難排解

## 模型箱子的左鍵沒反應

幾乎一定是缺少 hitbox。左鍵是一次攻擊，而承載模型的實體是原版攻擊碰不到的隱形
標記——點擊必須經由模型自己的 hitbox 抵達。

ModelEngine 會自動建立。**BetterModel** 會替名為 `hitbox` 的骨骼、或帶 `b_` /
`ob_` 前綴的骨骼建立。兩者皆無的模型不會有 hitbox 實體，所以沒有東西可以被打中。

外掛在啟動時就會針對這種情況發出警告，並列出模型實際擁有的骨骼。修法是加一個名為
`hitbox` 的群組，裡面放一顆與箱子等大的無貼圖方塊，然後重新載入模型外掛。

右鍵永遠不依賴 hitbox，所以「右鍵正常、左鍵沒反應」就是這個問題的典型徵兆。

## 某個設定看起來完全沒作用

檢查它的**縮排**。`reward-offset`、`reward-target`、`tasks` 以及其餘獎勵與時間軸
相關的鍵，都屬於 `cinematic:` 區塊**內部**，縮排兩個空格。放在第 0 欄的鍵會被當成
頂層設定、靜默忽略，而且不會有任何記錄。

這最常發生在解開範例註解的時候，因為註解所在的縮排可能與那個鍵需要的不同。

## 獎勵飛往錯誤的方向

`reward-offset` 不是那個旋鈕。它決定物品在哪裡**誕生**，無法瞄準。要用
`reward-target`，它是在相機的座標系裡度量的，所以箱子擺成什麼角度都不需要算數學：

```yaml
cinematic:
  reward-target: '0,0,1.2'    # 相機正前方 1.2 格
```

沒有它的話，水平速度是來自 `reward-velocity` 的一個固定世界軸推力，它不知道箱子
面向哪邊。

## 獎勵掉在箱子模型內部

對原地家族來說，`reward-offset` 的 **z** 是在箱子自己的座標系裡度量的——也就是
前方。把 z 設成 `0` 會讓獎勵出現在模型內部，大一點的模型會直接吞掉它。預設值是
`0,1.1,0.75`。

## 相機對著空地板

`setcam` 記錄的是你執行當下看的角度。如果之後用 `setmodel` 移動了模型，**要重新
執行 `setcam`**——否則相機仍然指著模型原本的位置。

## 運鏡會抖

把 `config.yml` 的 `cinematic.camera-teleport-duration` 設成 `1`。數值大於每 tick
的移動間隔時，客戶端會平滑相機的位置卻不平滑朝向，於是視線跑在位置前面，運鏡就
讀起來像在抖。

## 獎勵標題把輪播爆雷了

不要用 `title` 時間軸任務來公布獎勵。任務在從開箱起點起算的固定偏移觸發，而獎勵是
照自己的時鐘抵達的——所以一個在某個箱子上看起來剛好的延遲，在另一個箱子上會在輪播
中途觸發。

公布是內建的，會在真正的揭曉點觸發。用 `reward-title` 與 `reward-title-delay` 設定。

## 加了運鏡路徑之後,箱子的時間軸就失效了

箱子自己的 `tasks:` 會**取代**全伺服器的 `default-tasks`；兩者永遠不會合併。把你
還想要的那幾行預設複製進箱子裡。

## `/crate admin unplace <crate>` 說「not found」

`unplace` 吃的是**放置點 id**，不是箱子 id。它們是自動編號的 `<箱子>_<序號>`。
Tab 補全會列出來，或執行 `/crate admin places`。

## 什麼都沒發生,主控台也什麼都沒有

先看啟動時有沒有載入警告——外掛會回報解析失敗的箱子、發不出東西的獎勵、已經失效的
custom-item id，以及沒有 hitbox 的模型。

如果主控台真的乾淨，那可能是箱子**拒絕**了這次開箱：權限節點、冷卻、每日上限、
背包已滿或世界黑名單都會在**扣費之前**拒絕，而且每一種都會傳訊息告訴玩家是哪一個。

## 尋求協助

在資源討論串發文，附上：

* 你的 **`latest.log`**
* 出問題的那份**箱子 yml**

這兩樣加起來能立刻回答大部分問題。
